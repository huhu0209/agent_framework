1
怎么让上层不关心"调的是哪家模型"？

统一 LLM 调用抽象层，是整个框架的底层基石

D1
统一类型系统 — 框架拥有自己的类型
content 永远是 ContentBlock 数组，tool_use 按 Anthropic 方式建模
问题
每家 Provider 的消息格式完全不同（OpenAI 用 tool_calls 数组，Anthropic 用 content block），上层代码不可能适配所有格式
选择
Pydantic canonical types：types.py 定义统一消息模型，transform/ 子包做双向转换
放弃
❌ OpenAI 格式作为统一格式（Anthropic 解包太复杂）
❌ LangChain 式 dict 自由格式（无类型安全）
❌ 每个 Provider 一套类型（上层要写 provider-aware 代码）
代价
需要维护 transform/ 转换层；provider_extras 逃逸口让高级用法不污染核心类型
因果影响
→ D5 最小 Schema（ToolParameterSchema 也在 types.py 中定义） → D7 压缩器依赖 normalize
代码：llm/types.py · llm/transform/
D2
装饰器模式做弹性 — 重试+熔断不侵入 Provider
ResilientLLMAdapter 包装任意 ILLMAdapter，透明添加重试和熔断
问题
LLM API 经常 429/5xx/超时，但重试/熔断逻辑不应该混入 Provider 代码
选择
装饰器模式：ResilientLLMAdapter 实现同一个 ILLMAdapter 接口，内部包装重试（指数退避）+ 三状态熔断器
放弃
❌ 继承式弹性（RetryableOpenAIProvider）→ 每个 Provider 写一遍
❌ 第三方库 tenacity/backoff → 引入外部依赖
❌ 分布式熔断 Redis → 框架是单进程的
代价
流式响应中途断开不重试（只连接阶段重试）；熔断器内存状态不支持多进程
因果影响
→ D8 ReAct 循环只面向 ILLMAdapter，不知道背后有重试
代码：llm/resilient.py · llm/retry.py
D3
httpx over SDK — 零 SDK 版本耦合
三个 Provider 全部用 httpx.AsyncClient 直接调 HTTP API
问题
openai/anthropic/deepseek SDK 版本迭代快，API 签名经常变，引入三个 SDK 依赖树庞大
选择
裸 httpx.AsyncClient，自己控制超时粒度（connect/read/write/pool）、连接池、代理
放弃
❌ Provider 官方 SDK → 版本耦合，依赖树爆炸
❌ DeepSeek 继承 OpenAIProvider → 行为差异会让继承变脆
代价
必须自己实现各家 API 的请求/响应格式转换；但通过 transform/ 纯函数隔离了这部分复杂度
代码：llm/providers/*.py · llm/streaming.py
2
怎么让 Agent 能力可扩展，而不是硬编码？

工具注册、发现、路由与执行引擎

D4
注册表 + 前缀路由 — 三种来源统一调度
flat namespace dict，用 mcp__ / agent__ 前缀区分来源
问题
工具来自三个完全不同的来源：Python 函数（builtin）、JSON-RPC 子进程（MCP）、Agent 委派（agent）。各有不同的生命周期和错误处理
选择
注册表 dict[str, ToolSpec] + 前缀路由：mcp__* → MCP，agent__* → agent，其余 → builtin。5 阶段管线：权限→前Hook→执行→降级→后Hook
放弃
❌ 层级命名空间（mcp.server.tool）→ 简单前缀够用
❌ 装饰器注册 @tool → 显式注册更可调试
❌ 策略模式分发 → 3 种来源固定，无需抽象
代价
前缀约定是硬合约；注册重名抛 ValueError；MCP 工具绕过 executor（无超时/校验/截断保护）
因果影响
→ D9 子Agent注册为 run_subagent 工具 → D16 A2A 远程 Agent 也注册为工具
代码：tools/registry.py · tools/router.py · tools/degrader.py
D5
最小 JSON Schema — 跨 Provider 最大公约数
只支持 type/properties/required/description/enum/items，排除 oneOf/anyOf/$ref
问题
LLM 有时幻觉工具参数（缺字段、类型错），需要校验。但同一个 schema 要在 Anthropic/OpenAI/DeepSeek 三家的 tool definition 格式中都工作
选择
只支持 JSON Schema 的最小子集。ToolParameterSchema 定义在 llm/types.py（不在 tools/ 中），因为 LLM 层也需要它
放弃
❌ 完整 jsonschema 库 → 各家 Provider 不支持完整 JSON Schema
❌ Pydantic 模型校验 → MCP 工具的 schema 运行时动态到达，无法预定义
代价
工具参数必须设计为扁平结构；不能用 oneOf 做联合类型
因果来源
← D1 统一类型（schema 定义权归 LLM 层）
代码：llm/types.py:ToolParameterSchema · tools/validator.py
D6
5 阶段路由管线 — 权限/Hook/执行/降级 一条龙
权限检查 → 前Hook → 执行（含降级回退）→ 后Hook
问题
工具调用前需要安全检查、行为注入；调用后需要结果验证。这些关注点必须有序执行，不能跳步
选择
线性管线：权限（PermissionPipeline）→ 前Hook（可阻断/改参数）→ 执行+降级 → 后Hook（截断到 5000 字符防 Hook 进程爆）
放弃
❌ 中间件链 → Hook 系统已提供扩展性
❌ 事件溯源 → 线性管线更简单、更可审计
代价
管线阶段紧耦合在一个 dispatch() 方法中；后Hook 只看到截断结果
因果来源
← D14 四步权限（嵌入管线第一阶段）
代码：tools/router.py:dispatch()
D7
LLM 摘要压缩 — 保留语义的上下文窗口管理
75% 阈值触发，按 turn 分组保留最近 20 轮，旧消息 LLM 摘要
问题
长对话超出上下文窗口会报错，但直接删旧消息会丢失关键决策和状态
选择
Turn-based 滑动窗口：保留最近 20 轮，旧的用一个 LLM 调用生成 7 段式摘要（已完成/当前状态/关键文件/决策/错误/待办/上下文），注入为 UserMessage
放弃
❌ 简单删除 → 丢关键信息
❌ Token 级截断 → 可能切断 tool_call/result 配对
❌ 滚动摘要 → 累积误差
代价
压缩时多一次 LLM 调用；依赖 normalize_messages 确保压缩后格式合法（tools → llm 反向依赖）
代码：tools/context/compactor.py · tools/context/token_counter.py
3
怎么让推理策略可替换，而不是只有一种？

Agent 基类与 ReAct 推理循环，框架的核心推理引擎

D8
ReAct 作为不可约原子 — 所有策略的基础
最简单的支持工具调用的循环；PlanAndSolve/Reflection 都委托给它
问题
框架需要一个默认执行引擎。如果基础是 PlanAndSolve，你不能轻易降级为纯 ReAct；但从 ReAct 可以构建任何策略
选择
AgentLoop 状态机：调 LLM → 看 StopReason 分支 → END_TURN 结束 / TOOL_USE 调工具继续循环。所有外部依赖（LLM/工具/记忆/Hook）通过构造器注入
放弃
❌ 链/管线架构 → ReAct 本质是紧耦合循环
❌ 流式返回中间步骤 → 简化合约，避免并发竞争
代价
LLM 层必须返回 StopReason.TOOL_USE/END_TURN；工具必须返回 ToolResult(content=str)；计划注入会修改消息列表
因果来源
← D2 装饰器弹性（Loop 不知道背后有重试）
因果影响
→ D10 三策略都委托 AgentLoop → D14 编排器本身也是 AgentLoop
代码：agents/agent_loop.py · agents/base.py
D9
子Agent 工具化 — LLM 自主决定何时委派
run_subagent 是一个 ToolSpec；递归防护通过 RECURSIVE_TOOLS 集合实现
问题
复杂任务需要委派，但子 Agent 不应该是独立的层级体系——那需要全新的生命周期管理
选择
run_subagent 注册为普通工具，LLM 像调用其他工具一样调用它。子 Agent 继承所有工具但过滤掉 RECURSIVE_TOOLS = {"run_subagent", "task_create", "spawn_teammate"}，静态防止无限递归
放弃
❌ 父子树生命周期管理 → 太重
❌ 共享消息历史 → 破坏隔离性
❌ 动态递归层数限制 → 静态集合更安全可审计
代价
子Agent 返回纯字符串（非结构化）；共享 ILLMAdapter 和 ToolUseContext（同模型凭证、同工作目录）
因果来源
← D4 注册表+路由（基础设施复用：权限、Hook、降级全适用）
代码：agents/sub_agent.py
D10
三策略能力阶梯 — 可组合因为都委托 AgentLoop
ReAct（基础）→ PlanAndSolve（加分解）→ Reflection（加自评）
问题
不同复杂度的任务需要不同策略：简单任务直接 ReAct，复杂任务先规划再执行，质量敏感任务需要自我评估
选择
三种策略不是继承关系，而是包装关系：PlanAndSolve 每步创建新 AgentLoop，Reflection 每轮创建新 AgentLoop。理论上 PlanAndSolve 的每步可以用 ReflectionAgent
放弃
❌ 共享上下文执行步骤 → 上下文污染
❌ 增量计划调整 → 简化为整体重规划
❌ 思维树/束搜索 → 太复杂，线性计划+失败重规划更务实
代价
每步/每轮创建新 Loop = 无状态共享（文件系统中的 artifact 仍在）；Reflection 的评估维度（正确性/完整性/清晰度）硬编码
因果来源
← D8 ReAct 原子（所有策略都委托给它）
代码：agents/plan_and_solve.py · agents/reflection.py
4
怎么让安全、记忆、钩子横向切进去，而不侵入核心？

记忆管理、提示词组装、安全边界、会话转录、生命周期钩子、技能系统

D11
双层记忆 — 语义（启动注入）vs 情景（按需搜索）
两种根本不同的访问模式：一种零成本始终在，一种按查询付费
问题
短期详细日志和长期提炼知识有完全不同的存取需求。单层方案要么淹没长期记忆，要么丢失重要事件
选择
MemoryLayer 枚举只有两个值。语义层（Markdown + YAML frontmatter，启动时注入 system prompt）；情景层（按日期分区的追加式 Markdown 日志，关键词搜索）
放弃
❌ 统一存储 + 相关度阈值 → 混淆不同访问模式
❌ 三层模型（工作/短期/长期）→ 过度设计
❌ 向量数据库 → 文件数 < 50，不需要
代价
需要维护两种存储格式；语义记忆需要三阶段提取管线（对话→事件→知识，每次 3 个 LLM 调用）
因果影响
→ D12 文件即 DB（双层都用文件） → D13 LLM 评分（语义搜索不用向量，用 LLM 选文件）
代码：memory/types.py · memory/store.py（门面）
D12
文件系统即数据库 — 零基础设施部署
Memory/Transcript/Skills/Profiles 全用 Markdown/JSONL，不用 SQLite/Redis/向量库
问题
Agent 框架需要持久化多种数据，但引入数据库增加部署复杂度、丧失人可读性、需要 schema 迁移
选择
全文件：语义记忆用 Markdown+frontmatter，情景日志用日期分区 Markdown，Transcript 用 JSONL 追加写入，Skills 用 Markdown，索引用 MEMORY.md。关键路径原子写入（write-to-temp + os.replace）
放弃
❌ SQLite → 人不可读、需 schema
❌ Redis/向量库 → 外部依赖
❌ 单 JSON 数组文件 → 不支持追加写入
代价
文件数上限（语义记忆 50 个候选）；O(n) 线性搜索；不支持多会话并发写（显式标注在 docstring 中）；同步 IO（agent loop 单会话串行，无竞争）
因果来源
← D11 双层记忆（驱动了文件方案的选择） → D15 Teams 也用 JSONL 文件做消息总线
代码：memory/ · transcript/ · skills/
D13
LLM 评分召回 — 不用向量库，用 LLM 当裁判
列出所有文件摘要，让 LLM 选最相关的，适合小语料（<50 文件）
问题
语义记忆按文件存储，没有向量索引。需要选出与查询相关的文件
选择
两阶段：扫描所有 .md 文件的 frontmatter（name + description）→ 发给 LLM 要求返回 JSON {"selected": ["file1.md"]}。有路径穿越防护
放弃
❌ 向量嵌入 + 余弦相似度 → 需要嵌入模型+索引+重嵌入管线，< 50 文件不划算
❌ BM25/TF-IDF → "用户偏好 TypeScript" 搜不到 "语言偏好"
代价
每次语义搜索 1 次 LLM 调用（非零延迟和成本）；50 文件上限；LLM JSON 解析失败静默返回空
因果来源
← D11 双层记忆 + D12 文件即DB → 文件数小，LLM 评分可行
代码：memory/retriever.py
D14
四步级联权限 — DENY → MODE → ALLOW → ASK
确定性、可审计、短路的权限管道，不走 LLM 判断
问题
Agent 调用工具必须经过安全评估。权限决策必须快速、确定性、可审计
选择
4 步短路级联：① DENY（全局黑名单 + profile disallowed）→ ② MODE（deny-all/accept-all）→ ③ ALLOW（profile allowed 白名单）→ ④ ASK（根据工具注解：readOnly→自动允许，destructive→询问）
放弃
❌ 可配置优先级的规则引擎 → 固定级联不可误配
❌ 单个 trusted 布尔标记 → 太粗糙
❌ LLM 做安全判断 → 不确定性+延迟
代价
级联顺序固定（不能"模式 deny 但允许某个工具"）；注解需要预先注册
因果影响
→ D15 HITL（ASK 结果触发人工审批） → D6 路由管线（嵌入为第一阶段）
代码：safety/permissions.py
D15
子进程 Hook + HITL 异步门 — 安全隔离 + 人工介入
Hook 用子进程执行（防崩溃传播）；HITL 用 asyncio.Future（不阻塞事件循环）
问题
需要行为注入机制（Hook），且当权限返回 ASK 时，Agent Loop 要异步等待人类决策
选择
Hook：bash -c 子进程执行，exit code 语义：0=通过(可改参数)，2=注入消息，其他=阻断。JSON 上下文通过 stdin 管道传入
HITL：asyncio.Future 字典，Agent Loop await 挂起，UI 层调用 resolve() 恢复
放弃
❌ 进程内 Python 回调 → 有 bug 会崩框架
❌ 阻塞 input() → 冻结事件循环
❌ Redis 消息队列 → 框架是进程内的
代价
Hook 增加子进程启动延迟；JSON-in/exit-code-out 协议简单但受限；HITL 只支持进程内
因果来源
← D14 四步权限（ASK 结果需要 HITL 兜底）
代码：hooks/manager.py · safety/hitl.py
5
怎么让多个 Agent 协作，而不是只能单打独斗？

Orchestrator 规划、Team 总线、Task 管理、A2A 协议、可视化

D14
LLM 自路由编排 — Coordinator 本身就是 AgentLoop
没有硬编码分解逻辑；LLM 通过 spawn_worker/send_message/list_workers 工具自行编排
问题
单 Agent 处理复杂多面任务质量下降；需要分解子任务给专业 Worker 执行
选择
Coordinator 是一个 AgentLoop，只有 3 个编排工具。LLM 自己理解任务、决定分解方式、决定执行顺序。Worker 是叶节点（没有编排工具）
放弃
❌ 硬编码 DAG 执行器 → 无法适应新任务结构
❌ 层级递归分解 → Worker 不能再 spawn Worker
❌ MapReduce → 当前是顺序 spawn
代价
分解质量完全依赖 LLM；Worker 看不到 Coordinator 的对话（上下文隔离）；spawn 是 await 的（阻塞）
因果来源
← D8 ReAct 原子（编排器复用 AgentLoop 而非新建体系） ← D9 子Agent工具化（同样的 ToolSpec 模式）
代码：orchestrator/engine.py · orchestrator/coordinator_tools.py
D15
JSONL 文件消息总线 — 崩溃恢复优先
每个 Agent 一个 inbox.jsonl 文件；追加写入，读取后原子清空
问题
多个长生命周期 Agent 需要异步协作。进程崩溃后消息不能丢失
选择
inbox/<name>.jsonl，每条消息一行 JSON。读取用 write-to-temp + os.replace 原子清空。Teammate 持久循环，空闲时每 2 秒轮询 inbox
放弃
❌ asyncio.Queue → 进程崩溃消息全丢
❌ Redis/gRPC → 引入外部依赖
❌ WebSocket 推送 → 轮询 2 秒间隔够用
代价
2 秒轮询延迟；破坏性读取（处理中崩溃会丢未处理消息）；单进程限定
因果来源
← D12 文件即DB（与记忆/转录保持一致）
代码：teams/bus.py · teams/manager.py
D16
A2A 纯 ASGI — 跨进程 Agent 通信的最小实现
手写 ASGI（不依赖 FastAPI），HTTP+轮询，远程 Agent 注册为本地工具
问题
Teams 只在同一进程内工作。不同进程/容器/机器的 Agent 需要通信
选择
手写 ASGI 4 路由（agent-card 发现 / 提交任务 / 查询状态 / 取消）。Client 用 httpx 轮询（2 秒间隔，最长 300 秒）。register_as_tool() 让远程 Agent 变成本地工具
放弃
❌ gRPC → 需要生成 stubs + grpcio 依赖
❌ FastAPI/Starlette → 手写 ASGI 更轻，任何 ASGI server 都能跑
❌ WebSocket → 任务模型是提交-轮询，不需要流式
代价
任务状态纯内存（重启丢失）；2 秒轮询开销；API key 比较非常量时间（安全隐患）；无流式结果
因果来源
← D4 注册表+路由（register_as_tool() 复用整个工具调度体系） ← D9 子Agent工具化（同一个"一切皆工具"模式）
代码：a2a/server.py · a2a/client.py · a2a/models.py

🧭 跨层设计原则

一切皆工具

子Agent、远程Agent、团队协作、任务管理——全部注册为 ToolSpec。LLM 只需要一种交互方式

LLM 是组件，不是控制器

LLM 用于提取/评分/判断（管线内），但所有架构决策（权限级联/Hook执行/记忆合并）是确定性代码

构造器注入一切

AgentLoop 的所有外部依赖（LLM/工具/记忆/Hook/Task/Team）通过 __init__ 注入，默认 None，可独立测试

单进程异步优先

无分布式状态、无 Redis、无消息队列。熔断器内存态，消息总线文件态，事件总线 asyncio.Queue

优雅降级

JSON 解析失败、文件缺失、空目录——全部 warning + 空返回，不抛异常。系统设计为部分数据下仍可运行

逃逸口优于虚假通用

provider_extras、provider_event、ctx.extra——高级用法可以访问 Provider 特有功能，但不污染核心抽象
