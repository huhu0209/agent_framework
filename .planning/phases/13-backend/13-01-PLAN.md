    1. 逻辑正确性：条件分支是否覆盖所有路径？循环终止条件是否正确？返回值语义是否与文档一致？

    3. 错误处理：异常是否正确捕获和传播？SSE stream 中的异常处理是否完整？Redis 不可用时的降级是否合理？
    4. 设计模式：是否违反 SOLID？是否过度工程？文件组织是否合理？SessionManager 职责是否过重？
    5. 安全问题（Per D-05）：API 端点认证、输入验证、CORS 配置、敏感信息泄露、会话管理、错误信息泄露
    6. 框架层调用方式（Per D-07）：AgentFactory 是否正确使用 create_adapter？ToolUseContext 初始化是否完整？AgentLoop 参数传递是否正确？TranscriptWriter/TranscriptConsumer 使用是否正确？
    7. 死代码补充：ruff 无法检测到的死代码（条件分支不可达、未使用的 import 在 TYPE_CHECKING 外等）

    重点审查项（基于代码预读识别的高风险区域）：
    - main.py: CORS 配置（allow_methods=["*"]，allow_headers=["*"]），Redis 连接异常处理（静默吞没）
    - config: api_key 明文存储在 Settings 中（SecretStr？），api_key_must_not_be_empty 验证时机
    - models: SESSION_ID_RE 正则校验是否充分
    - session.py: TTL 淘汰中的 task 取消竞态、_append_history 同步 I/O 在 async 上下文中、JSONL history 的非原子读写、redis_client 的 Any 类型标注、_invalidate_list_cache 在并发下的正确性
    - chat.py: SSE stream 中的 agent error 异常消息泄露（str(exc)）、session_id 未校验归属权（任意用户可访问任意 session）、await asyncio.to_thread(sm._redis_set_messages, ...) 在 sm 没有活跃 Redis 时是否安全
    - agent_factory.py: ToolUseContext() 空构造是否足够、create_loop 缺少工作目录等参数

    Per D-06 完整数据流追踪 — 在 "## 数据流追踪" 章节为每个 API 端点绘制完整路径：
    - POST /api/v1/chat: HTTP Request → ChatRequest Pydantic 验证 → SessionManager.get_or_restore/create → AgentFactory.create_loop → AgentLoop.run → LoopEvent → _map_to_sse → SSE Response
    - GET /api/v1/chat/{session_id}: HTTP Request → session_id path 参数 → SessionManager.get_messages → 三层查找（内存/Redis/JSONL）→ HistoryResponse
    - GET /api/v1/sessions: HTTP Request → SessionManager.list_sessions → JSONL 读取 → Response
    - DELETE /api/v1/sessions/{session_id}: HTTP Request → SessionManager.delete_session → 文件删除 + JSONL 重写 → Response
    - PATCH /api/v1/sessions/{session_id}: HTTP Request → RenameRequest 验证 → SessionManager.update_title → JSONL 重写 → Response

    每个 issue 写入 REVIEW-BACKEND.md 对应文件章节下，使用 BKND-LOGIC-*（逻辑漏洞）、BKND-ARCH-*（设计问题）、BKND-SEC-*（安全漏洞）、BKND-DEAD-*（死代码补充）前缀。模块内按 CRITICAL → HIGH → MEDIUM → LOW 排序。
