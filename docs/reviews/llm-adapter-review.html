1. 架构总览

架构优点

  • 分层清晰 — 核心抽象层（types/base/transform/streaming/retry）与 Provider 实现层完全分离，新增 Provider 只需实现 ILLMAdapter 接口
  • 装饰器模式 — ResilientLLMAdapter 以组合方式包装任意 Provider，retry 和 circuit breaker 可独立开关
  • 纯函数转换 — transform/ 包全部是无副作用纯函数，天然可测试，Provider 之间共享逻辑零重复（DeepSeek 复用 OpenAI 转换）
  • 统一类型系统 — content 永远是 ContentBlock 数组，消除了 OpenAI string|array 二义性，上层代码无需关心 Provider 差异
  • 工厂函数 — create_adapter() 通过字符串映射动态导入 Provider，上层代码零耦合
  • 生命周期管理 — ILLMAdapter 定义 close() 抽象方法，ResilientLLMAdapter 委托给 Provider，支持 async context manager

3. 数据流分析

非流式请求路径

1
resilient.create_adapter() — 工厂函数根据 provider 名称通过 _PROVIDER_MAP 动态导入 Provider 类，创建 ResilientLLMAdapter 实例
↓
2
ResilientLLMAdapter.complete() — 检查 CircuitBreaker（allow_request()）→ 通过 retry_with_backoff() 包装内部 Provider
↓
3
Provider._build_request_body() — 调用 messages_to_openai/deepseek/anthropic() 转换消息格式，附加采样参数
↓
4
httpx.AsyncClient.post() — 发送 HTTP 请求。网络异常（httpx.ConnectError）转为 ServiceUnavailableError
↓
5
handle_http_error() + _parse_response() — 公共函数 handle_http_error() 按 HTTP 状态码映射到 typed 异常，响应体通过 parse_openai/anthropic_response() 转回统一类型
↓
6
ResilientLLMAdapter — 记录成功/失败到 CircuitBreaker，返回 CompletionResult

流式请求路径

1
ResilientLLMAdapter.stream() — 手动重试循环：检查 CircuitBreaker → 调用 provider.stream() → 尝试获取第一个事件（__anext__()）。仅连接阶段可重试
↓
2
Provider.stream() — httpx.stream("POST") 建立 SSE 连接，parse_sse_lines() 逐行解析为 JSON dict
↓
3
OpenAIStreamParser / AnthropicStreamParser — 维护增量拼接状态（tool_calls buffer / content_block index），每个 chunk 转为 StreamEvent 列表
↓
4
ResilientLLMAdapter — yield 第一个事件后，继续 async for event in stream 逐个 yield 后续事件。流完成后 record_success()，异常则 record_failure()
↓
5
StreamCollector (可选) — 消费端使用 feed() 累积事件，最终 collect() 得到完整 CompletionResult

数据流 — 设计亮点与已知限制

  • 错误提前转换 — Provider 在收到非 200 响应时通过 handle_http_error() 立即抛出 typed 异常，retry 层按 retryable 字段决策
  • 流式重试语义明确 — v2 重写后，retry 仅覆盖"建立连接 + 获取首个事件"阶段。一旦开始 yield，后续事件不受 retry 保护，语义清晰
  • Anthropic 双解析器 — Anthropic 流式事件类型远多于 OpenAI（message_start/content_block_start/delta/stop），需要独立的 AnthropicStreamParser 维护 index → block 映射
  • 流式超时静默化 — 三家 Provider 的 stream() 中，httpx.TimeoutException 和 httpx.ConnectError yield ERROR 事件而非 raise，circuit breaker 不会感知（新发现）

4. 各模块分析

types.py
统一类型系统 — 所有模块的基础
定义了完整的消息/内容块/工具/配置/结果/流式事件类型体系。content 永远是 ContentBlock 数组（消除 OpenAI string|array 二义性），ToolMessage 独立 role（内部用独立 role，转换时按目标格式合并）。

亮点：ThinkingBlock 预留了 signature 字段（Anthropic 回传校验），ThinkingConfig 用 budget_tokens 区分 provider 能力。provider_extras 字典允许上层透传各家特有参数，不污染统一接口。UsageStats 包含 cache_read_tokens/cache_creation_tokens。
257 lines
base.py
ILLMAdapter 抽象接口 + 异常层次 + 公共错误处理
ABC 定义 5 个方法：complete / stream / get_provider_info / health_check / close（v2 新增 close）。异常体系为 4 层继承：LLMAdapterError → RateLimitError / ServiceUnavailableError / InvalidRequestError / CircuitOpenError，每个异常自带 retryable 标记。

v2 新增：handle_http_error(response, provider_name) 公共函数，消除三家 Provider 的 _handle_error 重复代码。按 HTTP 状态码映射到 typed 异常，支持 retry-after 头解析。
195 lines
transform/ (包)
消息格式双向转换 — v2 拆分为 4 个子模块
_openai.py (183 行) — OpenAI ChatCompletions 格式互转。ThinkingBlock 静默丢弃，tool arguments JSON-stringified。
_anthropic.py (196 行) — Anthropic Messages API 格式互转。system 分离为顶层字段，tool_use/tool_result 是 content block，arguments 是 object。
_deepseek.py (112 行) — 复用 OpenAI 格式，追加 reasoning_content 支持（tool call 场景必须回传）。
_normalize.py (103 行) — 发送前修复：配对补 "(cancelled)"、同角色合并、不可变保证。

亮点：DeepSeek 复用 OpenAI 转换函数（code reuse via delegation），normalize_messages 通过 model_copy 保证不可变。
618 lines total (4 files)
streaming.py
SSE 解析 + 流式事件收集
三层设计：parse_sse_lines() 通用 SSE 行解析器（过滤 data: 前缀、处理 [DONE]）；OpenAIStreamParser 维护 tool_calls 增量拼接状态；StreamCollector 提供 text_stream / collect 两种消费方式。

亮点：OpenAIStreamParser 用 index → buffer dict 处理多个并行 tool call 的增量拼接，finish_reason 时输出完整 TOOL_USE_END 事件。StreamCollector.get_text_so_far() 支持实时预览已收集文本。
293 lines
retry.py
重试策略 + Circuit Breaker
重试：retry_with_backoff() 实现指数退避 + jitter + retry-after 优先。should_retry() 按 retryable 标记决策，400 错误立即失败。

Circuit Breaker：经典三态机 CLOSED → OPEN → HALF_OPEN。连续 N 次失败触发熔断，冷却期后允许探测，探测成功 M 次恢复。

v2 改进：state property 不再有副作用。状态转换通过显式的 _check_and_transition() 方法触发（在 allow_request() 内部调用），state property 只返回当前值，调试/监控场景安全。
262 lines
resilient.py
门面层 — 工厂函数 + 弹性包装器 + 生命周期
ResilientLLMAdapter 组合 Provider + RetryConfig + CircuitBreaker，对外实现 ILLMAdapter 接口。每个方法先检查断路器，再通过 retry 委托给内部 Provider。

create_adapter() 工厂函数通过 _PROVIDER_MAP 字符串映射动态导入 Provider 类。

v2 改进：实现 close() 委托给 Provider，支持 async context manager。stream() 重写为手动重试循环，仅覆盖连接建立阶段。

openai_provider.py
OpenAI ChatCompletions Provider
最标准的 Provider 实现。_build_request_body() 调用 messages_to_openai() + tools_to_openai() + build_openai_sampling_params()。流式使用 OpenAIStreamParser。

特点：支持 reasoning_effort（o 系列）、provider_extras 透传。handle_http_error() 委托到 base.py 公共函数。默认模型 gpt-5，最大上下文 400K。

DeepSeek V4 Provider (OpenAI 兼容接口)

协议差异最大的 Provider。system 是顶层字段、tool_use/tool_result 是 content block、arguments 是 object。需要独立的 AnthropicStreamParser 处理 6 种事件类型（message_start/content_block_start/delta/content_block_stop/message_delta/message_stop）。

特点：Extended thinking 支持 budget_tokens + signature 回传。auto-calculate max_tokens（budget + 8192）。支持 cache_control / pdf / computer_use 通过 provider_extras。默认模型 claude-sonnet-4-6。

亮点：372 行覆盖了 Anthropic 的所有关键差异点。AnthropicStreamParser 维护 content_block_index → block 映射，支持并行 tool call。

6. 问题追踪 (v2)

MEDIUM v2 新发现 三家 Provider 样板代码重复 (~80%)
openai_provider.py / deepseek_provider.py / anthropic_provider.py
三个 Provider 共享高度相似的代码：complete()（发请求 + 解析响应 + 异常处理）、stream()（SSE 连接 + 解析 + 超时 yield ERROR）、close()、__aenter__/__aexit__、超时处理。唯一真正的差异是 _build_request_body() 和 _parse_response()。

三家合计 855 行，其中约 600 行是重复样板。
推荐方案：提取 BaseHTTPProvider 基类，实现通用的 complete/stream/close/context manager。子类只需实现 _build_request_body()、_parse_response()、get_provider_info()。

预计减少：~400 行重复代码。但需要谨慎 — Anthropic stream 有独立的 AnthropicStreamParser，可能导致基类 stream() 仍需 hook point。
MEDIUM v2 新发现 流式超时/连接错误静默化，Circuit Breaker 不感知
anthropic_provider.py:326-330, openai_provider.py, deepseek_provider.py
三家 Provider 的 stream() 方法中，httpx.TimeoutException 和 httpx.ConnectError 被捕获后 yield 一个 ERROR StreamEvent，而非 raise LLMAdapterError。

这意味着：
  1. 消费者必须检查 ERROR 事件（容易遗漏）
  2. ResilientLLMAdapter 的 stream() 会正常 yield ERROR 事件后 record_success()，Circuit Breaker 不会感知这次失败
  3. 重试机制不会被触发
推荐方案：在 Provider.stream() 中不捕获这些异常，让它们传播到 ResilientLLMAdapter.stream() 的 retry 循环中。或者，在 ResilientLLMAdapter.stream() 的事件 yield 循环中检测 ERROR 事件并 record_failure()。
MEDIUM v2 新发现 OpenAI 默认 base URL 疑似非标准地址
openai_provider.py:49
OPENAI_BASE_URL = "https://api.openseek.com/v1" — 这不是标准 OpenAI API 地址（api.openai.com）。

可能是：代理/中转站（有意为之）、拼写错误、或测试用占位符。如果是有意为之，建议添加注释说明。
改进方向：确认意图。如果是代理，添加注释。如果是默认值，改为标准地址或移除默认值（强制配置）。
LOW v2 新发现 messages_to_openai 参数缺少泛型类型
transform/_openai.py:19
messages_to_openai(messages: list) 的参数类型应为 list[Message]，缺少泛型参数。其他转换函数（messages_to_deepseek、messages_to_anthropic）都有正确的类型注解。
改进方向：改为 messages: list[Message]。
LOW v2 新发现 _calculate_delay 私有函数被外部模块导入
resilient.py:80
from .retry import _calculate_delay — 下划线前缀表示模块私有，但被 resilient.py 直接导入使用。这破坏了封装约定。

当前场景是合理的（stream() 手动重试需要计算延迟），但 API 设计上应考虑是否公开。
改进方向：方案 A — 将 _calculate_delay 重命名为 calculate_delay（公开）。方案 B — 在 retry.py 提供一个专用的 stream_retry_with_backoff() 工具函数。
LOW v2 新发现 importlib 在函数体内导入
resilient.py:148
import importlib 出现在 _import_provider_class() 函数体内，而非模块顶部。Python 惯例是顶层导入。

功能上无影响（延迟导入，每次调用不会重复 import），但不遵循 PEP 8 风格。
改进方向：将 import importlib 移到模块顶部。

7. 依赖关系

依赖分析结论

  • 无循环依赖 — 依赖严格单向：Provider → transform/streaming → types/base，resilient → providers + retry + base
  • types.py 是所有模块的根依赖 — 257 行的类型定义被所有其他文件 import，变更时需注意影响面
  • Provider 之间零耦合 — openai_provider 不 import deepseek_provider，各自只依赖核心层
  • resilient.py 是唯一知道所有 Provider 的模块 — 通过 _PROVIDER_MAP 动态导入，上层代码不感知具体 Provider 类
  • DeepSeek 复用 OpenAI 转换 — _deepseek.py 委托给 _openai.py（code reuse），不引入重复逻辑
  • v2 拆分未引入新依赖 — transform/ 包对外接口不变，只改了内部组织

8. 总结

LLM Adapter 模块经过 v1 review 后的系统化改进，架构成熟度显著提升。v1 指出的 7 个问题（3 MEDIUM + 2 LOW + 2 测试覆盖）全部解决，测试从 439 行增长到 2,400 行（+447%），transform.py 拆分为按 Provider 组织的包，生命周期管理完整实现。

架构亮点：统一类型系统消除 OpenAI string|array 二义性；normalize_messages 保证不可变；Anthropic Provider 完整覆盖协议差异；handle_http_error 消除重复；依赖关系严格单向、无循环依赖；流式重试语义清晰明确。

v2 新发现：三家 Provider 约 80% 样板代码重复（可通过 BaseHTTPProvider 基类消除 ~400 行）；流式超时/连接错误 yield ERROR 事件而非 raise，Circuit Breaker 不感知；OpenAI 默认 base URL 疑似非标准地址。这些都是下一轮迭代的改进点。

总体评分：9.0/10 — v1: 8.5 → v2: 9.0。高质量的 LLM 抽象层，Provider 隔离、类型系统、测试覆盖和依赖管理均表现优秀。Provider 样板去重和流式错误传播是主要提升空间。
