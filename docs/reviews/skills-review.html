1. 架构总览

架构优点

  • 职责单一 — manifest 只管解析，registry 只管注册/发现，tool 只管 LLM 集成。每个文件 <200 行。
  • 两级加载 — L1 轻量目录注入 system prompt，L2 按需加载完整正文，避免 context 污染。
  • 不可变数据模型 — 全部使用 frozen=True dataclass，防止意外修改。
  • 显式错误类型 — SkillLoadResult 用 is_error 标记替代异常/前缀判断。

2. 数据流分析

扫描路径 — SKILL.md 发现与注册

1
SkillRegistry.__init__() — 接收 skills_dirs: list[Path]，按优先级排序（personal > project）
↓
2
_full_refresh() — 清空 _documents，逐目录调用 _scan_dir()
↓
3
_scan_dir() — rglob("SKILL.md") 递归扫描，调用 _parse_skill_document() 解析
↓
4
_parse_skill_document() — 分离 frontmatter 和 body，调用 parse_frontmatter_lines() 解析键值对
↓
5
SkillManifest + SkillDocument — 组装不可变对象，first-wins 策略存入 _documents

L1 加载路径 — System Prompt 注入

1
assembler.py — 构造 PromptAssembler 时传入 skill_registry
↓
2
describe_available() — 调用 _maybe_refresh() 检查 mtime，返回每 skill 一行摘要
↓
3
注入为 <SKILLS> block 插入 system prompt

L2 加载路径 — Agent 按需调用

1
agent_loop.py — 注册 load_skill 工具，注入 skill_registry 到 ctx.extra
↓
2
_handle_load_skill() — 从 ctx.extra 取 registry，调用 load_full_text(name)
↓
3
load_full_text() — 返回 XML 包裹的正文 + references 索引（最多 10 个文件）

数据流 — 设计决策

  • mtime 自动发现 — 每次 L1/L2 调用前检查目录 mtime，变化则触发全量刷新。简单有效，适合 skill 数量少的场景。
  • first-wins 优先级 — personal 目录先扫描，同名 skill 覆盖 project 级别，支持用户自定义。
  • references 截断 — 最多显示 10 个参考文件 + 剩余数量提示，防止 context 爆炸。

4. 问题清单

MEDIUM hooks 字段声明但从未解析
manifest.py:25 — SkillManifest.hooks
SkillManifest 定义了 hooks: dict[str, Any] | None = None，但 registry.py:_scan_dir() 中从未从 frontmatter 读取 hooks 配置。如果用户在 SKILL.md 中写了 hooks:，会被静默忽略。

此外，当前 parse_frontmatter_lines() 只支持扁平键值对，无法解析嵌套 dict，因此即使读取也无法正确解析。
改进方向： 短期：在文档中标注 hooks 为保留字段（reserved），避免用户困惑。长期：如需支持 hooks，需先扩展 frontmatter 解析器支持嵌套结构，或在 hooks 场景明确时再添加。
LOW allowed_tools / model 字段解析但未使用
registry.py:108-109 — _scan_dir()
allowed_tools 和 model 从 frontmatter 解析并存入 SkillManifest，但在整个 tool/agent 层没有任何地方消费这些字段。allowed_tools 未用于限制工具调用范围，model 未用于覆盖模型选择。
改进方向： 作为预留字段可接受，但建议添加注释标注其用途和待实现状态，或在 agent_loop 集成时按需启用。当前不影响功能。
LOW _scan_dir 存在冗余的存在性检查
registry.py:94 vs registry.py:87
_scan_dir() 第一行 if not root.exists(): return 与调用方 _full_refresh() 中的 if d.exists(): 重复。虽然防御性编程无害，但在当前调用链中不会触发。
改进方向： 保留即可。作为内部方法的多一层防御是合理的，尤其在 _scan_dir 可能被其他路径调用的未来场景下。
LOW tool.py description 拼接可读性
tool.py:28-31
ToolSpec.description 用多个字符串字面量拼接（隐式 concat），虽然 Python 语法正确，但在 diff 审查时不如单行或 textwrap.dedent 直观。
改进方向： 可选优化。当前不影响功能，描述文本较短，拼接方式可接受。

5. 依赖关系

依赖分析结论

  • 单向依赖 — tool → registry → manifest → frontmatter，无循环。
  • 外部依赖极少 — 仅依赖 memory/frontmatter.py（frontmatter 解析）和 tools/types.py / llm/types.py（工具类型），耦合度低。
  • 消费者清晰 — agent_loop.py 负责注册工具，assembler.py 负责注入目录，职责边界明确。

7. 总结

Skills 模块是一个设计精良的渐进式加载系统。四个文件共 301 行代码，职责划分清晰：manifest 管数据模型和解析，registry 管发现和注册，tool 管 LLM 集成，__init__ 管 API 边界。两级加载（L1 目录 + L2 正文）有效控制了 context 开销，first-wins 多目录策略支持 personal 覆盖 project。

关键改进：历经 12 次提交迭代，解决了 XML 注入风险（quoteattr）、显式错误类型（SkillLoadResult）、自动发现一致性（全量刷新）、references 截断提示等关键问题。每次改进都有对应测试覆盖。

遗留项：hooks 字段为保留声明，需等 frontmatter 解析器支持嵌套结构后再实现。allowed_tools 和 model 为预解析字段，等 agent 系统集成时启用。

总体评分：9/10 — 模块体量小但设计完整，错误处理严谨，测试覆盖充分（52 tests），代码风格一致。
