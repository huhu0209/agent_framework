2. 架构总览

架构优点

  • 极简分层 — types（数据）、router（逻辑）、__init__（导出）三文件各司其职，总计 136 行
  • 依赖注入 — SkillRegistry 通过构造函数可选注入，无 registry 时命令系统独立工作
  • 不可变设计 — ResolvedCommand 和 SlashCommand 均为 frozen dataclass
  • 优雅降级 — 未知命令、加载失败、非 invocable skill 全部降级为普通消息，不抛异常
  • 优先级链清晰 — builtin > skill > fallback，用户无法覆盖框架命令

3. 数据流分析

路径 1: Builtin 命令解析

1
resolve(user_input) — 检查 / 前缀，split(maxsplit=1) 提取 name + args
↓
2
_builtins[name] — 在 builtin 字典中查找，handler 非 None 则调用
↓
3
返回 ResolvedCommand(is_command=True, content=handler结果, source=BUILTIN)

路径 2: Skill 加载

1
resolve() — builtin 未命中，if self._skill_registry 进入 skill 路径
↓
2
_try_load_skill() — get_manifest() 查询 manifest，检查 user_invocable
↓
3
load_full_text() — 加载 skill 正文，body.replace("$ARGUMENTS", args) 替换占位符
↓
4
返回 ResolvedCommand(is_command=True, content=替换后正文, source=SKILL, skill_loaded=True)

路径 3: 降级路径

1
非 / 前缀 / 空 / / 未知命令 / skill 不可用 / 加载失败
↓
2
关键：所有降级路径最终汇聚到 resolve() 末行的 return ResolvedCommand(is_command=False, content=user_input)，保留原始输入

数据流设计决策

  • 降级不抛异常 — 所有失败路径静默降级，保证 REPL 不中断
  • 原始输入保留 — 降级时 content 保留用户原始输入（含 args），不截断不丢失
  • $ARGUMENTS 不转义 — 用户参数直接注入 skill 正文，调用方负责 LLM prompt 安全
  • Builtin 优先 — 同名 skill 会被同名 builtin 遮蔽（如 /help）

5. 问题清单 — 第三轮发现

MEDIUM resolve() 缺少异常安全保护
router.py:48-51
resolve() 的 skill 路径调用 _try_load_skill()，后者调用 registry.get_manifest() 和 registry.load_full_text()。如果 registry 实现有 bug 抛出意外异常（如 OSError、AttributeError），异常会穿透 resolve() 到达调用方。

这与模块的"优雅降级、永不抛异常"设计理念矛盾。前两轮 review 的所有降级路径都是返回 ResolvedCommand，但缺少对意外异常的兜底。
建议修复：在 resolve() 的 skill 路径添加 try/except：
try: result = self._try_load_skill(...); except Exception: logger.debug(...); pass
确保任何 registry 异常都被捕获并降级，不暴露给上层。
MEDIUM _try_load_skill 失败返回值永远不会被使用
router.py:55-69, 48-53
_try_load_skill() 在 manifest 缺失或加载失败时返回 ResolvedCommand(is_command=False, content=f"/{name}")。

但 resolve() 中的调用逻辑是：if result.is_command: return result。当 is_command=False 时，代码不会提前返回，而是 fall through 到末行的 return ResolvedCommand(is_command=False, content=user_input)。

这意味着 _try_load_skill 失败时构建的 ResolvedCommand（含 content=f"/{name}"）永远不会被使用。方法创建了一个无用的中间对象，增加了理解成本。
建议修复：将 _try_load_skill 返回类型改为 ResolvedCommand | None。成功时返回 ResolvedCommand，失败时返回 None。resolve() 改为 if result is not None: return result。
这样失败语义更清晰——"没有结果"而不是"有一个结果但你要忽略它"。
MEDIUM _cmd_help 对每个 skill 重复调用 get_manifest
router.py:95-100
_cmd_help() 先调用 registry.get_names() 获取所有 skill 名称，然后对每个名称调用 registry.get_manifest(name)。

get_manifest() 内部调用 _maybe_refresh()，每次都检查所有 skill 目录的 mtime。N 个 skill = N 次 mtime 检查。虽然单次检查开销小（stat 系统调用），但属于不必要的重复——实际上只需要检查一次。
建议修复：在 SkillRegistry 中添加 get_user_invocable_skills() -> list[tuple[str, str]] 方法，一次性返回所有用户可调用的 skill 名称和描述。避免 router 循环调用 get_manifest。
或者接受当前实现——在 skill 数量 < 50 的场景下性能影响可忽略。
LOW 无 builtin 命令注册公共 API
router.py:80-86
_register_builtins() 是私有方法，硬编码注册 /help。应用层无法通过公共 API 注册自定义 builtin（如 /version、/status），必须直接操作 router._builtins 字典。

测试中就是这么做的：router._builtins["noop"] = SlashCommand(...)。
建议：添加 register_builtin(cmd: SlashCommand) 公共方法，或保持现状（YAGNI——当前只有 /help 一个 builtin，不需要注册 API）。
LOW _try_load_skill 日志丢失 args 信息
router.py:63, 68
logger.debug() 调用只记录 skill name 和失败原因，不记录用户传入的 args。排查"为什么 /deploy --env prod 没触发 skill"时缺少关键信息。

例如：logger.debug("Skill '%s' 不可调用 (manifest=%s)", name, manifest) 中，--env prod 部分没有被记录。
建议：在 debug 日志中加入 args：logger.debug("Skill '%s' 不可调用, args='%s' (manifest=%s)", name, args, manifest)。
LOW 缺少异常安全性测试
test_command_router.py
测试覆盖了 registry 返回错误结果的场景（is_error=True），但没有测试 registry 方法本身抛出异常时 resolve() 的行为。

如果添加异常安全保护（MEDIUM-1），应同步添加测试：mock get_manifest 抛出 OSError，验证 resolve() 返回降级结果。
建议：添加 test_registry_exception_falls_through 测试用例。
LOW create_skill 辅助函数不校验 meta key
tests/helpers.py:8-29
create_skill() 使用 **meta_extra 接受任意键值对写入 SKILL.md frontmatter。拼写错误（如 user_invocible 代替 user_invocable）会静默通过，创建一个字段名错误的 skill 文件。

这不是 bug——helper 的设计就是灵活的——但可能导致测试中出现难以排查的假阴性。
建议：可在 create_skill 中添加合法 key 白名单检查，或在测试中添加一个反面测试验证拼写错误的 key 被正确忽略。

依赖分析结论

  • 无循环依赖 — Commands 单向依赖 Skills，Skills 不感知 Commands
