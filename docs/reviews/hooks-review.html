2. 架构总览

架构优点

  • 不可变设计 — HookConfig、HookContext、HookResult 均为 frozen dataclass，HookContext 用 dataclasses.replace 创建新实例
  • 优雅降级 — 子进程超时、OSError、JSON 解析失败全部降级为 HookResult，不抛异常

  • 循环依赖规避 — TYPE_CHECKING 守卫 + lazy import，集成点不产生 import 时依赖

3. 退出码协议

Hooks 系统的核心契约是子进程退出码语义。这是整个模块最关键的设计决策，所有行为都围绕这个协议展开。

退出码 语义 HookResult 字段 集成点行为
0 继续（pass-through） blocked=False，可选解析 stdout 中的 {"updatedInput": {...}} PreToolUse: 允许执行，可选修改参数；PostToolUse: 无动作
1 或其他 阻止（block） blocked=True，stderr = 阻止原因 PreToolUse: 返回 [Hook blocked] 错误；PostToolUse: 忽略（工具已执行）
2 注入消息（inject） inject_message=stderr or stdout PostToolUse: 追加 [Hook supplement]；SessionStart: 注入 [Hook] 消息

数据流：PreToolUse 完整路径

1
ToolRouter.dispatch() — 权限检查通过后，构造 HookContext(tool_name, tool_input)
↓
2
HookManager.fire() — replace(context, session_id=...) 自动填充 session_id，遍历匹配的 hooks
↓
3
_execute_command() — bash -c <command>，stdin 注入 JSON context，asyncio.wait_for 超时控制
↓
4
_parse_exit() — 解析退出码、stdout、stderr 为 HookResult
↓
5
ToolRouter — blocked 返回错误；updated_input 替换参数；继续执行工具

数据流：SessionStart 路径

1
AgentLoop.run() — 初始化消息列表后，构造 HookContext(hook_event_name="SessionStart")
↓
2
fire(SessionStart) — 匹配所有 matcher="*" 的 hooks（SessionStart 不涉及 tool_name 匹配）
↓
3
遍历 results，有 inject_message 则追加 UserMessage([TextBlock(text="[Hook] ...")]) 到 messages

5. 问题清单

MEDIUM fire() 中 once hooks 的列表修改在迭代中进行
manager.py:104-112
fire() 先收集 to_remove 列表，迭代结束后再 remove()。这避免了在迭代中修改列表的问题，设计正确。

但 list.remove() 的时间复杂度是 O(n)，对于 once hooks 较多的场景有性能开销。更重要的是，如果同一个 HookConfig 被注册两次（虽然不太可能），remove() 只会移除第一个匹配项。

实际风险：低。once hooks 通常数量极少（1-3 个），且 HookConfig 是 frozen dataclass，同一实例重复注册的可能性极低。当前实现是正确的，只是不够健壮。
建议：保持现状。如果未来 once hooks 数量增长，可改为用 index-based 切片或 list comprehension 重建列表。
MEDIUM command 注入风险 — 用户配置的 command 直接传入 bash -c
manager.py:120-121
asyncio.create_subprocess_exec("bash", "-c", config.command) 直接执行用户在 JSON 配置文件中指定的 command。

这本身是设计意图（Hook 的目的就是执行用户指定的命令），但缺少对 command 内容的任何验证或审计日志。load_from_json() 只检查空字符串，不检查危险命令模式（如 rm -rf）。

注意：这是 Hook 系统的核心功能——执行用户指定的命令。限制 command 内容会破坏其用途。但缺少 audit trail 是一个安全审计缺口。
建议：在 _execute_command() 中添加 logger.info("Executing hook: %s (event=%s, matcher=%s)", config.command[:100], config.event.value, config.matcher)，记录所有 Hook 执行。command 截断到 100 字符防止日志膨胀。
MEDIUM updated_input 缺少类型验证 — Hook 可注入任意字段
manager.py:26-27
_parse_exit() 解析 stdout 中的 {"updatedInput": {...}} 时，直接 data.get("updatedInput") 取值，不验证返回值的类型。

如果 Hook 脚本输出 {"updatedInput": "not a dict"}，updated_input 将是一个字符串而非字典。在 ToolRouter 中，这会被传入 ToolCall(arguments=hr.updated_input)，可能导致下游类型错误。

更极端的情况：{"updatedInput": null} 或 {"updatedInput": 42} 都不会被拦截。
建议修复：在 _parse_exit() 中添加类型检查：
if isinstance(updated, dict): pass，否则设为 None。
一行代码，防御性编程，防止 Hook 脚本意外输出非 dict 类型。
LOW load_from_json 的 JSON 嵌套结构解析缺少防御性检查
manager.py:72-86
entry.get("hooks", []) 假设返回的是列表。如果 JSON 中 "hooks" 字段是字符串或其他非列表类型，for h in entry.get("hooks", []) 会遍历字符串的字符（Python 中字符串可迭代），产生奇怪的错误。

类似地，h.get("type", "command") 和 h.get("timeout", 30) 假设 h 是字典，但未验证。
建议：在 for h in ... 前添加 if not isinstance(hooks_list, list): continue。或保持现状（YAGNI——配置文件由用户控制，格式错误会在第一次使用时暴露）。
LOW stdin JSON 中 tool_input 或空对象的选择缺少注释
manager.py:130
"tool_input": context.tool_input or {} — 当 tool_input 为 None 时降级为空字典。这是正确的设计（JSON 不支持 Python None 作为值，但 {} 是合法的），但缺少注释说明为什么选择 {} 而非 None。

同理 "tool_result": context.tool_result or "" — 空字符串而非 null。
建议：添加一行注释说明降级策略：确保 JSON 序列化输出始终是合法的 JSON 值（dict/str），而非 null。或者保持现状——选择是显而易见的。
LOW 缺少 HookConfig 验证 — timeout 可为负数
types.py:27
HookConfig.timeout 类型是 int，默认 30，但没有最小值约束。如果 JSON 配置中指定 "timeout": -1，asyncio.wait_for 会立即超时。timeout: 0 同理。

从 JSON 加载时也不验证 timeout 值的范围。
建议：在 load_from_json() 中添加 timeout=max(1, h.get("timeout", 30))，或使用 __post_init__ 验证器（但 frozen dataclass 的 __post_init__ 有限制）。
LOW SessionStart hook 不传递 tool_name — matcher 语义不对称
agents/agent_loop.py:246
HookContext(hook_event_name=HookEvent.SESSION_START.value) 构造时未传 tool_name，默认为 None。

在 _match() 中，tool_name=None 只匹配 matcher="*"。这意味着 SessionStart hook 的 matcher 只能是 "*"，其他值永远不匹配。但这个约束没有被文档化。

如果用户配置了 "SessionStart": [{"matcher": "any", "hooks": [...]}]，该 hook 会被静默忽略。
建议：在 HookManager docstring 或 load_from_json() 中添加注释说明：SessionStart 事件的 matcher 应始终为 "*"。
LOW HookResult.exit_code 与 blocked 语义耦合不严格
manager.py:35
退出码非 0 且非 2 时，_parse_exit() 设置 blocked=True。但 HookResult 的类型定义允许手动构造 HookResult(exit_code=0, blocked=True)（exit 0 但 blocked）。

没有构造约束阻止这种语义上矛盾的实例。虽然内部代码路径不会产生这样的结果，但作为 frozen dataclass 的公共 API，缺少验证。
建议：保持现状（YAGNI——HookResult 仅由内部代码构造，外部使用者只读取）。如需严格，可用 __post_init__ 验证。

8. 总结

Hooks 模块是一个设计精良、实现扎实的行为扩展系统。207 行代码实现了完整的 Hook 注册、匹配、Shell 执行、JSON 配置加载，以及与 ToolRouter（PreToolUse/PostToolUse）和 AgentLoop（SessionStart）的深度集成。39 个测试覆盖了所有公共方法、退出码协议、错误路径和集成场景。

核心优势：退出码协议（0/1/2）设计清晰且与 Claude Code 兼容；trusted 门控零开销跳过；frozen dataclass 保证不可变性；优雅降级贯穿全系统（超时、OSError、JSON 错误）；TYPE_CHECKING 避免循环依赖。

问题清单：3 个 MEDIUM + 5 个 LOW。核心关注点是updatedInput 缺少类型验证（Hook 可注入非 dict 值到 ToolCall.arguments）和缺少执行审计日志（Hook 执行无 INFO 级别记录）。这些不影响功能正确性，但在安全审计和防御性编程方面有改进空间。

总体评分：8.8/10 — 架构简洁，退出码协议设计优秀，测试充分。修复 updatedInput 类型验证和添加审计日志后可达 9.5+。

亮点总结

  • 退出码协议 — 0/1/2 三态设计简洁强大，覆盖 pass/block/inject 三种行为，与 Claude Code 协议一致
  • Trusted 门控 — 未信任时 fire() 直接返回 []，不执行任何子进程，零安全风险
  • 健壮的 JSON 加载 — 文件不存在、格式错误、无效事件名、空命令、非列表条目全部优雅降级
  • stdin JSON 注入 — Hook 脚本通过 stdin 接收结构化上下文，设计干净
  • 集成管线清晰 — Permission → PreToolUse → Execute → PostToolUse，职责明确
  • Once 机制 — 单次触发后自动移除，适合初始化和一次性通知场景
  • 零第三方依赖 — 全部使用 Python 标准库
