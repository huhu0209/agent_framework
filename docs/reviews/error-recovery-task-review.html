1. 架构总览

架构优点

  • 分层清晰 — LLM 错误恢复（retry/circuit breaker）、Task 持久化（DAG 管理）、运行时执行（runner）三层解耦，各层可独立测试
  • 装饰器模式 — ResilientLLMAdapter 作为透明包装器，不侵入 Provider 实现，任何 ILLMAdapter 都能获得重试+断路能力
  • 不可变数据模型 — Task 使用 frozen=True dataclass，配合 dataclasses.replace() 更新，避免意外突变
  • 异步安全设计 — TaskRunner 使用 asyncio.Semaphore 控制并发，asyncio.Queue 通知机制无锁安全

2. 数据流分析

LLM 调用容错路径 — complete()

1
ResilientLLMAdapter.complete() — 检查断路器状态，OPEN 则直接抛 CircuitOpenError
↓
2
retry_with_backoff() — 包裹 provider.complete()，按 RetryConfig 执行最多 N+1 次尝试
↓
3
should_retry() — 429/5xx → 可重试（指数退避 + jitter），400 → 不重试直接抛出
↓
4
CircuitBreaker.record_success/failure() — 成功重置失败计数，失败累计并可能触发熔断（CLOSED → OPEN）

Task 执行路径 — 后台任务

1
TaskRunner.run(task_id, prompt) — 将任务状态设为 IN_PROGRESS，创建 asyncio.Task
↓
2
TaskRunner._execute() — 获取信号量，启动 AgentLoop 实例，用 asyncio.wait_for 包裹执行
↓
3
AgentLoop.run() — 消费事件流，done → COMPLETED，error → FAILED
↓
4
asyncio.TimeoutError — 超时捕获，状态设为 FAILED，通知入 Queue
↓
5
AgentLoop → drain_notifications() — 主循环每轮拉取，作为 UserMessage 注入对话

数据流 — 已解决 / 已知限制

  • 流式重试边界清晰 — stream() 仅在连接建立阶段（取第一个事件前）重试，连接建立后的错误直接上报，避免数据混乱
  • 超时与状态一致 — TaskRunner 超时后先更新 RuntimeTask 内存状态，再持久化到 TaskManager，finally 块确保通知入队
  • 已知限制 — TaskManager 非线程安全，仅适用于 asyncio 单线程（已在文档注释中声明）

3. 各模块分析

llm/base.py
异常类型体系 + HTTP 错误映射
定义了 4 层异常继承：LLMAdapterError → RateLimitError(429) / ServiceUnavailableError(5xx) / InvalidRequestError(400) / CircuitOpenError(断路器)。

每个异常携带 provider、status_code、retry_after、retryable 四元组，handle_http_error() 将 httpx Response 统一转为 typed 异常。

亮点：异常设计面向重试决策，retryable 属性让 retry.py 无需 if-else 判断状态码。
195 lines
llm/retry.py
重试策略 + Circuit Breaker 状态机
RetryConfig 冻结配置，_calculate_delay() 实现指数退避 + jitter，优先使用服务端 retry-after header。

CircuitBreaker 三态模型：CLOSED → OPEN（连续 N 次失败）→ HALF_OPEN（冷却期后探测）→ CLOSED（探测成功 M 次）。allow_request() 隐式触发 OPEN→HALF_OPEN 转换，API 简洁无副作用。

亮点：jitter 因子防止雷群效应，success_threshold=2 避免单次成功就恢复的抖动。
262 lines
llm/resilient.py
Retry + Circuit Breaker 组合包装器
complete() 先检查断路器 → retry_with_backoff 包裹 → 成功记成功 / 失败记失败。

stream() 手动重试逻辑更精细：仅在 __anext__ 阶段重试，一旦产出事件则不再重试（数据流语义正确）。

工厂函数 create_adapter() 按 provider 名称动态创建，支持 deepseek/openai/anthropic。
187 lines
tasks/types.py
Task 数据模型（持久化 + 运行时）
Task — frozen dataclass，包含 blocked_by/blocks 双向依赖字段，支持 DAG 拓扑。6 种状态枚举 TaskStatus。

RuntimeTask — 可变 dataclass，记录运行时状态/输出/错误，不持久化。

亮点：双层模型分离关注点，Task 只做结构，RuntimeTask 只做执行状态。
46 lines
tasks/manager.py
持久化任务 DAG CRUD
每个任务独立 JSON 文件存储。create() 带上限检查（12），update() 带状态机验证。

双向依赖维护：add_blocked_by/add_blocks 联动更新对端 Task。_clear_dependency() 在任务完成时自动清除下游依赖。

安全：_path() 拒绝非数字 ID（防止路径遍历），_load_all() 容忍损坏文件。
234 lines
tasks/runner.py
后台异步任务执行器
asyncio.Semaphore(max_concurrent=3) 控制并发上限。asyncio.wait_for 实现超时（默认 300s）。

超时/异常均在 finally 块中完成两件事：(1) RuntimeTask 入通知队列 (2) 从 _running 字典移除。

亮点：超时后 TaskManager.update 也用 try-except 包裹，防止"超时后的状态更新失败"掩盖超时信息。
115 lines
tasks/tools.py
4 个 LLM 可调用 Task 工具
task_create/task_update/task_list/task_get 完整 CRUD。

每个 handler 捕获具体异常（TaskLimitError/TaskNotFoundError/TaskConflictError/TaskStatusError）并返回 is_error=True 的 ToolResult。

亮点：错误信息直接来自异常 message，对 LLM 友好（如"已有任务正在执行中"）。
147 lines
agents/agent_loop.py
ReAct 循环 — 错误恢复编排中心
多层错误恢复：(1) LLM 异常 → LoopEvent(type="error") 终止循环 (2) MAX_TOKENS → 视为错误 (3) 计划偏离 → 连续 N 步未推进时 ABORT (4) 上下文压缩 circuit breaker → 连续 3 次失败跳过。

TaskRunner 集成：每轮 drain_notifications() 拉取后台任务结果，作为 <task-notification> 注入对话。

亮点：SessionStart hook 注入、计划上下文不累积（每轮清理旧注入再重新注入）。
375 lines

4. 问题清单

HIGH 已修复 TaskRunner.run() 无幂等性保护 — 重复调用同一 task_id
tasks/runner.py:42-47
run() 直接创建 asyncio.Task 并写入 _running[task_id]。如果对同一 task_id 调用两次，旧的 asyncio.Task 会被覆盖但仍在运行，造成：(1) 内存泄漏 (2) 两个 AgentLoop 同时执行同一任务 (3) 两个任务完成通知入队，可能导致状态混乱。
已修复：在 run() 开头添加 if task_id in self._running: return 前置检查，并增加 test_run_idempotent_same_task_id 测试验证。
HIGH 已修复 TaskManager 并发竞态 — count_active() + create() 非原子
tasks/manager.py:46-61
create() 调用 count_active() 检查上限，然后写入文件。如果两个协程在 await 之间交替执行，上限检查可能失效。update() 中的 _find_in_progress() + 状态更新也不是原子的。
已修复：引入 asyncio.Lock，将 create() 和 update() 改为 async 方法，所有读写操作在锁内完成。所有调用方（tools.py、runner.py、测试）同步更新为 await 调用。
MEDIUM 已修复 CircuitBreaker 状态属性有副作用陷阱
llm/retry.py:203-206
state 属性是只读的，但 allow_request() 会隐式触发 OPEN → HALF_OPEN 转换。如果外部代码先读取 state 再调用 allow_request()，看到的状态可能不一致。这在监控/调试场景中可能造成困惑。
已修复：state 属性现在也调用 _check_and_transition()，确保读取状态时自动完成 OPEN→HALF_OPEN 转换。测试从 test_state_property_no_side_effects 更新为 test_state_property_triggers_transition。
MEDIUM 已修复 AgentLoop 中 RuntimeTaskStatus 导入位置不够理想
agents/agent_loop.py:239
from agent_framework.tasks.types import RuntimeTaskStatus 在 run() 方法体内导入。每次调用 run() 都会执行一次 import 语句。
已修复：将 RuntimeTaskStatus 导入移到模块顶层（在 TYPE_CHECKING 块之后），消除方法体内的延迟导入。
MEDIUM 已修复 _apply_changes 中依赖关系更新缺少事务性
tasks/manager.py:196-218
_apply_changes() 在更新双向依赖时，逐个写入对端 Task。如果中途写入失败（如磁盘满），会出现"单向依赖"的不一致状态。
已修复：引入 pending_writes 列表，先收集所有需要更新的 Task 对象，再批量写入。确保要么全部构建成功再写入，要么写入前就失败（不会留下部分更新）。
LOW ResilientLLMAdapter.stream() 中 _calculate_delay 延迟导入
llm/resilient.py:80
from .retry import _calculate_delay 在 stream() 方法体内部导入，这是因为文件顶部已从 retry.py 导入了多个公开符号。这个延迟导入是为了避免循环/冗余，但 _calculate_delay 实际上可以直接在顶部导入（它是纯函数，无副作用）。
改进方向： 将 _calculate_delay 加入文件顶部的导入列表，或将其提升为 retry.py 的公开 API（去掉下划线前缀）。
LOW task_list 工具的 DELETED 状态显示符号不够直观
tasks/tools.py:66
status_mark 字典中 DELETED 用 "d" 标记，FAILED 用 "!"。在 ASCII 列表中区分度不高，特别是当 LLM 看到这个列表时可能不理解 "d" 的含义。
改进方向： 考虑使用更明确的符号如 "X" 表示 DELETED，或在列表头部添加图例说明。
LOW TaskManager._load_all() 每次全量扫描磁盘
tasks/manager.py:135-142
list_all()、count_active()、_find_in_progress()、_clear_dependency() 都调用 _load_all()，每次都扫描磁盘读取所有 JSON 文件。当任务数量增加时，这会成为性能瓶颈。当前上限 12 个任务，性能不是问题，但值得记录。
改进方向： 如果未来任务上限提高，考虑引入内存缓存（如 _cache: dict[str, Task]），在 write 时更新缓存。

5. 依赖关系

依赖分析结论

  • 无循环依赖 — Task 系统和 LLM 错误恢复层完全独立，仅通过 agent_loop.py 在运行时集成
  • 异常体系下沉 — base.py 定义在底层，retry/resilient 依赖它而非反过来
  • tools.py 窄接口 — 只依赖 TaskManager（不依赖 runner），工具层不知道后台执行细节
  • 唯一关注点 — agent_loop.py 是唯一直接依赖 TaskRunner 的模块，集成点单一

7. 总结

Error Recovery 和 Task 系统展现了成熟的工程实践：LLM 错误恢复层通过 ResilientLLMAdapter 装饰器模式将 retry + circuit breaker 透明化，任何 Provider 无需修改即获得容错能力；Task 系统以 JSON 文件为持久化介质，用 frozen dataclass + 状态机验证保证了数据一致性。两者通过 agent_loop.py 的 drain 通知机制优雅集成，模块间零耦合。

关键亮点：异常类型体系的 retryable 属性设计消除了重试逻辑中的状态码判断；CircuitBreaker 的三态模型（含 HALF_OPEN 探测）和 success_threshold=2 避免了抖动恢复；TaskManager 的路径遍历防御和损坏文件容错体现了防御式编程。

待关注项：LOW 级别问题（_calculate_delay 延迟导入、task_list DELETED 符号不直观、_load_all 全量扫描）均为代码风格和远期性能优化，不影响当前功能正确性。

总体评分：9.0/10 — 架构清晰、测试充分（78 个测试 100% 通过）、异常处理全面、并发安全已加固，是一个高质量的基础设施模块。
